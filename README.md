# Órbita — Game Planning Dashboard

App desktop (Electron + React + TypeScript + SQLite) para planejar jogos e trabalhar com agentes (Claude Code, Codex, Gemini CLI e OpenCode) usando as CLIs e os logins que voce ja tem. Nao pede chaves de API nem cobra nada alem do que essas CLIs ja usam.

```bash
npm install
npm run dev     # abre a janela com hot reload
npm run build   # compila para out/
npm start       # roda a versao compilada
```

## Instalar no macOS e no Linux

Roda em Windows, macOS e Linux com o mesmo codigo. Use Node 24 (o mesmo do CI) e deixe as CLIs (claude, codex, gemini, opencode) no PATH do seu shell: aberto pelo Finder/menu, o app importa o PATH do shell de login (`$SHELL -ilc`), entao CLIs instaladas via npm, Homebrew ou nvm sao encontradas.

```bash
npm install
npm run dist    # instalador do sistema atual em dist/: .dmg no macOS, .AppImage e .deb no Linux (.exe no Windows)
```

Windows e Linux nao sao assinados; o macOS so e assinado e notarizado quando o CI tem as credenciais da Apple (ver `build/macos-signing.md`). Um `.dmg` sem assinatura baixado dos artefatos do CI chega em quarentena e o Gatekeeper bloqueia a primeira abertura: tente abrir uma vez e depois use Ajustes do Sistema > Privacidade e Seguranca > Abrir Mesmo Assim (no macOS 15+ o botao direito > Abrir nao basta), ou rode `xattr -dr com.apple.quarantine /Applications/Orbita.app`. Um `.dmg` gerado localmente com `npm run dist` nao fica em quarentena.

## Como funciona

- **Projetos**: pastas dentro de Documentos abertas no Claude Code (`~/.claude.json`) mais as que voce adicionar com "Adicionar pasta". So esses projetos podem ser lidos/executados pelo app.
- **Tarefas**: cada projeto tem varias tarefas, cada uma com seu proprio chat e historico (esquerda: projetos, busca, tarefas, Configuracoes; centro: o chat da tarefa; direita, opcional: Roadmap, Problemas e Documentos do projeto). Voce pode renomear, arquivar (nao apaga mensagens, arquivos nem worktrees) e buscar pelo titulo ou pelo texto das mensagens.
- **Provedores por tarefa**: no chat voce escolhe provedor, conta (Claude), modelo e esforco; a escolha fica gravada na tarefa e vale a partir da proxima execucao. Trocar de provedor nao apaga nem esconde o historico: a tarefa tem uma unica linha do tempo, com cada resposta rotulada pelo provedor/modelo/esforco que a gerou.
- **Sessoes nativas**: cada (tarefa, provedor, conta) retoma exatamente a sua sessao (`--resume <id>`, `exec resume <id>`, `--session <id>`; nunca "a ultima"). Sessoes de plataformas diferentes nao sao intercambiaveis: ao usar um provedor, perfil ou sessao que nao viu a conversa, o app monta o contexto pertinente (memoria da tarefa e historico) como um **pedido de aprovacao** e **retem a mensagem: nenhum agente e iniciado antes da sua decisao**. O cartao acima do campo de mensagem mostra o destinatario completo (provedor, conta, modelo, esforco, pasta e escopo), a mensagem e o conteudo exato, e oferece tres acoes: **aprovar e executar**, **executar sem contexto** ou **cancelar o envio**. Sem decisao no prazo, ao reiniciar ou ao cancelar, nada inicia e o texto fica recuperavel (ver "Consentimento de contexto").
- **Execucao**: cada mensagem roda a CLI em modo headless (a mensagem vai pelo stdin, nunca na linha de comando). Falhas, cancelamentos e interrupcoes ficam visiveis e gravadas (`concluida`, `falhou`, `cancelada`); cancelar encerra o processo e seus descendentes; fechar o app cancela o que estiver rodando; ao reabrir, execucoes interrompidas sao marcadas como falha sem duplicar mensagens. Permissoes compatíveis passam pelas regras e pelo pop-up do app (permitir uma vez, sempre permitir ou negar); a tradução para a política nativa depende do provedor. Ações que o modo headless não consegue perguntar continuam aparecendo como falha/nota; use "Terminal" na tarefa para continuar de forma interativa.
- **Worktree quando pedido**: conversar e ler arquivos nao exige Git. O botao de isolamento cria `<projeto>/.worktrees/task-<id>-<slug>` numa branch propria; problemas (pins) usam `.worktrees/pin-<id>-<slug>`. Mudar a pasta encerra sessoes nativas e cancela pedidos de contexto antigos, mantendo seu texto recuperavel. O historico so segue para a nova sessao com sua aprovacao.
- **Integrar e limpar worktrees**: na visao geral, selecione uma worktree no painel de branch e confira **Previa da integracao**. O destino e a branch atualmente aberta na pasta principal; origem e destino precisam estar limpos. **Iniciar integracao** prepara o merge local sem commit e pausa para revisao. Resolva conflitos na pasta de destino, marque as resolucoes com `git add` no terminal e atualize a revisao; **Concluir integracao** cria o commit. **Abortar integracao** desfaz as alteracoes do merge no destino. A pendencia permanece ao reabrir; agentes, comandos e commits comuns ficam bloqueados no destino ate concluir ou abortar. Operacoes Git externas continuam sob controle do terminal.
- **Limpeza separada**: **Previa da limpeza** e **Remover worktree** exigem todos os commits integrados, registro Git valido e pasta sem alteracoes, arquivos novos, ignorados, submodulos ou operacoes pendentes. Arquivos copiados na criacao, como `.env`, precisam ser preservados ou removidos manualmente primeiro. A branch fica no Git; tarefas e problemas voltam a pasta principal com sessoes novas, preservando conversas e evidencias. Push e PR continuam com suas confirmacoes existentes. Nada e integrado, removido ou publicado automaticamente.
- **Recuperacao**: se a pasta foi removida e o app parou antes de atualizar as tarefas, **Finalizar limpeza** conclui os vinculos somente apos verificar que a pasta e seu registro Git continuam ausentes. Se a integracao foi encerrada manualmente no terminal e a revisao ficou desatualizada, **Encerrar revisao desatualizada** limpa apenas o registro do app, com confirmacao e sem operacao Git pendente; arquivos e commits ficam preservados.
- **Problemas (pins)**: ficam no SQLite do app; "Abrir tarefa" cria/abre a tarefa ligada ao problema e "Terminal isolado" abre o agente numa worktree dele.

Arquivos marcados no indice como `skip-worktree` ou `assume-unchanged` podem ocultar alteracoes do Git. O app recusa integracao, conclusao, aborto ou limpeza que dependam desse estado oculto; retire essas marcas no terminal e revise novamente. A limpeza nunca usa `--force` nem apaga a branch.

## Planejamento e produção

1. Na home, registre um item na to-do e escolha seu projeto. **Preparar tarefa** cria um chat vinculado e coloca texto/imagens no compositor; nada é enviado automaticamente. **Abrir tarefa** reutiliza esse vínculo. Excluir a tarefa limpa o vínculo e permite preparar outra. O agente da lista é uma sugestão; confirme provedor/modelo no chat.
2. Em **Etapas de trabalho**, adicione título e ordem para cada fase da tarefa. **Preparar no chat** deixa a ordem editável antes do envio. Uma execução concluída fica em **Revisar resultado**; confira mensagens, arquivos e testes e clique em **Aceitar etapa** para liberar a próxima. **Pedir correção** permite nova execução. Falha/cancelamento podem ser retomados; reiniciar não dispara nada.
3. Em **Comandos do projeto**, configure programa, argumentos em array JSON e finalidade (teste, build ou jogo). **Executar** inicia o comando na pasta da tarefa, inclusive sua worktree, sem inferência. Para Godot, ative a integração no organizador e use o painel descrito abaixo.

A to-do fica no SQLite, com revisão para detectar gravações concorrentes. A lista antiga do localStorage é importada uma vez e preservada como cópia de recuperação; listas inválidas mostram erro sem sobrescrever essa cópia. O compositor valida seus próprios limites de anexos (até seis por envio). Texto e imagens de novos itens só são limpos quando a gravação é confirmada.

Etapas usam o mesmo chat e consentimento de contexto existentes. Concluir uma CLI não significa que o usuário aceitou o resultado. Comandos locais têm histórico por tarefa (20 execuções mais recentes na interface), saída limitada a 1.000.000 caracteres com aviso, exit code, duração e cancelamento da árvore de processos. Teste/build têm teto de 15 minutos; execução de jogo, duas horas. Fechar normalmente cancela; encerramento forçado deixa a execução marcada como interrompida na próxima abertura. Nenhum comando é retomado automaticamente.

Comandos e agentes não executam simultaneamente na mesma pasta pelo dashboard. São executáveis diretos, sem shell ou wrappers .cmd/.bat: para npm, use node.exe com o caminho de npm-cli.js como primeiro argumento, seguido de ["run","test"] ou ["run","build"]. No macOS/Linux o programa pode ser o próprio `npm` (resolvido pelo `which`; é um script com shebang, executado sem shell) ou `node` com o caminho de npm-cli.js. Scripts locais podem alterar arquivos, como fariam num terminal; revise antes de executar.

Os logs locais registram o que o processo devolveu; não alimentam a memória ou prompts de IA automaticamente e não autorizam pular testes futuros. Builds, templates de exportação e gameplay de um jogo real ainda precisam de validação no projeto escolhido.

Na visão geral do projeto, **Produção** reúne três registros locais:

- **Assets**: cadastre um arquivo relativo à pasta do projeto, com tipo, tags, origem e licença. Capturar uma versão guarda uma cópia imutável pelo SHA-256 na pasta de dados do app. Alterar o arquivo de trabalho não altera essa cópia; use **Capturar nova versão** para registrar a alteração. Aprovação/rejeição vale para o hash exibido, nunca para todas as versões. Capturar conteúdo igual reutiliza a revisão existente. Repetir o cadastro do mesmo caminho mantém os metadados do catálogo. Imagens têm preview; outros formatos ficam identificados por nome, tamanho e hash.
- **Playtests**: registre o observado, cenário, esperado, resultado, gravidade, notas e até seis screenshots; opcionalmente selecione o build testado. Para criar um problema, escreva seu título e a ordem de correção. Observações, imagens e histórico ficam no painel humano: não são copiados para o prompt ou memória do agente. **Abrir tarefa** reutiliza o problema ligado. Resolver o playtest é uma decisão separada da conclusão da tarefa.
- **Builds**: selecione um comando local concluído com exit 0 e informe o caminho relativo de um arquivo distribuível na pasta usada pelo comando. O app guarda a cópia e o comando de origem, versão e plataforma. Exit 0 registra sucesso do processo; o aceite de qualidade exige revisão humana. Excluir a tarefa de origem preserva o build e o registro do comando, removendo só os vínculos vivos.

**Exportar cópia** exige aprovação e verifica novamente a integridade. O destino é escolhido numa janela nativa; escolha um nome novo, pois arquivos existentes não são sobrescritos. Nada é publicado ou executado ao exportar. Os snapshots ficam em `production`, dentro da pasta de dados (ver "Banco de dados e migracao"); inclua essa pasta e o banco no backup. Há um teto de 512 MiB por asset/build e um arquivo por build (para pastas, gere um ZIP com seu comando local). Não há compactação automática, varredura de assets, validação de licença nem limpeza automática das versões; o catálogo registra o que você informou.

**Editar metadados** permite corrigir nome, tipo, licença, origem e tags dos assets; nome, versão, plataforma e notas das builds; título, severidade e notas dos playtests. Arquivo de origem, snapshots, aprovação por hash, comando, observações e screenshots permanecem preservados. Uma edição concorrente é recusada para você conferir os dados atuais, mantendo o rascunho.

**Arquivar** retira o registro da lista ativa e **Restaurar** o traz de volta. O filtro inclui ativos, arquivados ou todos; vínculos antigos a builds continuam disponíveis. Novos playtests selecionam builds ativas. Arquivar preserva arquivos e evidências.

Em Assets, a retenção manual mantém de 1 a 100 versões recentes por asset, além de todas as aprovadas, pendentes e fixadas. A prévia identifica somente versões antigas rejeitadas e não fixadas; confira e confirme antes de remover. Um snapshot só é apagado quando nenhuma versão ativa nem build de qualquer projeto usa seu hash. Builds e screenshots são mantidos. Os IDs e metadados das versões removidas permanecem no banco para evitar reutilização; capturar o mesmo conteúdo novamente recupera o registro e sua revisão anterior. Falha ao liberar um arquivo mantém seus bytes e aparece no resultado; uma nova prévia permite tentar novamente. Não há limpeza agendada.

## Godot local e consultas sob demanda

No menu do organizador, abra **Configurar organizador…**, marque **Ativar integração Godot** e informe o executável local; vazio usa `godot` no PATH. A configuração vale somente para os projetos desse organizador. Ativar a opção não inicia engine nem IA. O painel **Godot local** aparece nas tarefas que têm `project.godot` na pasta atual, inclusive worktrees; os metadados são lidos ao abrir o painel.

O fluxo inicial atende **Godot 4, GDScript e exportação Windows**:

1. **Verificar instalação Godot** confere versão e opções do binário. Escolha importar recursos, verificar um script, executar a cena principal/outra cena, abrir o editor ou exportar. **Preparar comando para revisão** salva o programa e os argumentos; **Executar comando Godot** é uma ação separada. Trocar de pasta, organizador, configuração ou binário exige nova preparação. Importação usa `--import`; verificar script usa `--check-only --script`, sem substituir testes do jogo.
2. Para exportar, instale os templates correspondentes à versão da engine e configure no editor um preset **Windows Desktop com PCK embutido**. Escolha um `.exe` novo dentro de uma pasta existente e vazia do projeto. A integração inicial recusa C#, GDExtension e bibliotecas externas; arquivos auxiliares também impedem registrar o executável como build completo. Para outros formatos, use comandos locais explícitos e prepare seu próprio pacote.
3. Confira o histórico e os diagnósticos. Erros reconhecidos fazem o comando falhar mesmo com exit 0; saída truncada também exige nova verificação. **Registrar build desta exportação** captura o executável como snapshot pendente. Revise o hash em **Produção → Builds**, vincule um playtest e, após avaliação humana, use o fluxo de integração da worktree. Nada é aprovado, integrado ou publicado automaticamente.

Nos chats e delegações com MCP compatível, somente agentes invocados dentro de um organizador com Godot ativo recebem três ferramentas locais de leitura: `godot_project` (configuração e referências), `godot_scene` (nós, recursos e propriedades de cenas textuais) e `godot_diagnostics` (diagnósticos agrupados de um arquivo de log escolhido). Desativar Godot ou mover o projeto revoga novas consultas; agentes já iniciados fora desse organizador não ganham ferramentas ao ativar a opção. Pai e filhos continuam sujeitos à pasta, ao escopo e à identidade da execução.

As respostas iniciais são limitadas por `queryChars`, com continuação por offset e hash. Propriedades, detalhes e texto bruto permanecem consultáveis; instâncias, herança, valores padrão da engine e recursos binários não são resolvidos pelo leitor textual. A ferramenta de diagnóstico lê somente um `.log`/`.txt` explicitamente informado dentro da pasta autorizada. O campo opcional **Arquivo de log** prepara `--log-file` para gerar esse arquivo; o histórico privado de comandos do dashboard não é entregue aos agentes automaticamente.

As consultas não executam Godot nem acrescentam uma chamada de IA. Os três schemas entram apenas nas invocações elegíveis; o agente pede detalhes quando precisa deles. Isso pode reduzir payload e leituras repetidas, mas schemas e chamadas também têm custo: os testes medem caracteres, não economia real de tokens nem qualidade de um jogo. A integração MCP atual cobre Claude, Codex e OpenCode; Gemini e o terminal interativo não recebem essas ferramentas. O painel de comandos locais funciona independentemente do provedor de IA.

## Backup e restauração

Em **Configurações > Dados**, **Criar backup…** grava uma pasta nova no destino escolhido: banco SQLite, anexos das conversas, snapshots de assets/builds, screenshots de playtests e `linkedin/perfil.md`, `rascunhos/` e `videos/`. O manifesto registra tamanho e SHA-256; guarde a pasta inteira. Arquivos dos projetos e worktrees, logins/configurações e sessões nativas das CLIs, cofre do LinkedIn, caches e preferências de navegação do Electron ficam fora. Faça uma cópia própria dos projetos.

**Selecionar backup…** verifica esquema, integridade e arquivos referenciados e mostra a prévia. **Restaurar e reiniciar** exige confirmação, prepara uma cópia independente e aplica a troca antes de abrir o banco no próximo início. O estado anterior ganha um backup em `backups/` na pasta de dados; um diário permite recuperar os originais se a troca for interrompida. Execute com agentes/comandos/logins parados. A pasta de backup externa deve ficar fora da pasta de dados do app.

A restauração pela interface exige banco e evidências atuais legíveis e íntegros para gerar essa cópia de segurança. Se essa verificação falhar, a preparação é recusada antes de reiniciar. Falha/interrupção na aplicação preserva os originais; se o app não conseguir concluir, os detalhes ficam em `diagnostics.log` e a preparação permanece em `.restore-pending` para nova tentativa.

Se o banco estiver corrompido e o app nem abrir, feche todas as instâncias e **renomeie a pasta de dados inteira para preservá-la**, sem apagar arquivos. O caminho aparece no erro de abertura; normalmente é `%APPDATA%\gaming-planning-dashboard` (Windows), `~/Library/Application Support/gaming-planning-dashboard` (macOS) ou `~/.config/gaming-planning-dashboard` (Linux). Reabra a Órbita para criar uma instalação vazia no caminho original e use **Configurações > Dados** para restaurar o backup. Um backup automático guardado na pasta preservada também pode ser selecionado. Os dados danificados continuam na pasta renomeada para investigação; credenciais externas das CLIs permanecem em seus diretórios próprios. Esse procedimento manual foi verificado com um banco corrompido sintético, snapshots e screenshots locais.

Histórico, to-do, etapas, revisões e uso informado são preservados. Anexos/screenshots e referências ao conteúdo próprio do LinkedIn são ajustados se a pasta de dados mudar; projetos externos mantêm seus caminhos. Pacotes aprovados e seus hashes de auditoria não são reescritos. As conversas começam sessões de IA novas, pois os arquivos externos das sessões não foram copiados; envios e aprovações pendentes expiram e nada roda sozinho. Reconecte o LinkedIn após restaurar. Backups são locais e manuais, sem compactação, nuvem ou retenção automática.

## Configuracoes

- **Provedores**: caminho, versao e capacidades detectadas de cada CLI, estado de login (consultas gratuitas, sem inferencia), variaveis de ambiente relevantes (so os nomes) e a ultima falha (categoria e texto sem segredos). Log em `diagnostics.log` na pasta de dados (URLs de login, tokens e chaves sao removidos).
- **Contas Claude**: "Principal" usa `~/.claude`. Contas novas usam `~/.claude-account-<id>`; perfis antigos mantem a pasta. O login roda `claude auth login` oculto, com estados (desconectado/conectando/conectado/erro), tempo limite de 5 minutos, cancelamento e um login por perfil; o estado e confirmado por `claude auth status` no ambiente do perfil. Se duas contas apontarem para a mesma pasta o app avisa (nada e apagado ou copiado). Credenciais herdadas do ambiente (`ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`, `CLAUDE_CODE_OAUTH_TOKEN`) sao ignoradas nos processos filhos dos perfis Claude para nao sobrepor o login da conta. Nao ha botao de login fora de Configuracoes.
- **Uso da conta Claude** (5 horas/semana): endpoint nao documentado, opcional; se falhar mostra o ultimo valor visto e nao afeta login nem chat.
- **Delegacao entre provedores**: ver abaixo.

## Modelos, esforco e contexto

- Catalogos: Codex pelo App Server (`model/list`), OpenCode por `opencode models --verbose` (variantes = esforco, janela do modelo), Claude pelos apelidos e niveis do `--help` (a CLI nao lista modelos por conta; um id completo pode ser digitado e a CLI valida), Gemini sem catalogo e sem esforco (nenhuma configuracao de raciocinio comprovada na versao instalada; so id de modelo digitado). Nada e substituido em silencio: sem escolha, o app nao passa flag nenhuma e a CLI usa o padrao dela; escolhas invalidas sao recusadas com o motivo.
- Indicador de contexto no chat: **contexto ocupado**, **janela do modelo** e **consumo** (tokens processados) sao coisas diferentes e aparecem separadas; cotas da conta ficam em Configuracoes. Percentual so aparece quando o numero e a janela sao conhecidos; estimativas levam "≈/estimado"; ausencia de dado aparece como "indisponivel" (nunca 0%). Fonte e horario da medida sao mostrados.

## Delegacao entre provedores

Um agente (Claude, Codex ou OpenCode) recebe a ferramenta MCP local `delegate_to_agent` e pode pedir a outro provedor uma analise (`read`) ou uma implementacao delimitada (`edit`, com `paths` opcionais). O dashboard executa o filho na pasta da tarefa do pai, mostra a atividade no chat, grava tudo (tabela `delegations`) e devolve o resultado ao pai como saida da ferramenta.

- Um nivel apenas: o filho nunca recebe a ferramenta. O agente nao escolhe pasta nem comandos; so objetivo, provedor, modelo/esforco, modo, escopo e contexto minimo (sem credenciais).
- Leitura e limitada pelo executor: Claude so recebe `Read/Grep/Glob`, Codex usa `-s read-only`, Gemini `--approval-mode plan`, OpenCode permissoes `edit/bash/write: deny`. Se algo mudar mesmo assim, a delegacao avisa.
- Um escritor por area: enquanto uma delegacao de edicao roda, outras tarefas nao executam naquela pasta. Timeout, limite por tarefa, provedores permitidos e edicao permitida sao configuraveis; o pai cancelado cancela os filhos; duas falhas seguidas para o mesmo provedor bloqueiam novas tentativas.
- Modelo indisponivel = recusa com a explicacao (sem trocar por outro).
- O servidor MCP escuta so em `127.0.0.1`, com token por execucao. O Gemini CLI so le servidores MCP de arquivos de configuracao (que o app nao altera), entao ele e destino, nao origem: recebe so o pacote ja aprovado na entrada e nao tem consulta incremental.
- O retorno ao pai e um **envelope curto**: estado, arquivos alterados, alertas (fora do escopo, modo leitura que alterou arquivos), erro, conclusao (alvo de 3.000 caracteres; se houver corte e rotulado "EXTRATO", nao "resumo") e a referencia ao **artefato** com o resultado completo, paginavel por `read_task_context`. Estado, falha, violacoes e arquivos nunca sao descartados pelo alvo de tamanho. O filho e instruido a terminar com um unico bloco `[CONCLUSAO]` (resultado, testes/evidencias, arquivos, bloqueios; sem raciocinio privado). O dashboard prefere o evento final nativo da CLI quando ele existe e reconhece o bloco por regra local; ausente, duplicado ou sem fechamento, nada e adivinhado e o envelope traz o extrato rotulado. O bloco e uma **declaracao do agente**: nao substitui o estado, o erro nem as violacoes observados, e "testes nao executados" ou bloco incompleto viram alerta.
- **Agentes nomeados**: o usuario cadastra um nome, um provedor e um modelo (e, opcionalmente, o esforco), como "Fabricio" = Codex + GPT-6 Luna. Ao salvar (IPC `setAgentAliases`) o nome precisa ser unico (sem diferenciar maiusculas nem acentos) e nao ser o de um provedor, e provedor/modelo/esforco sao validados no catalogo, o mesmo teste da delegacao. A lista vai na descricao da ferramenta `delegate_to_agent` (campo `agent`), recalculada a cada execucao: quando o usuario diz "delegue para o Fabricio", o agente passa `agent: "Fabricio"` e a dashboard resolve `codex / gpt-6-luna`. `agent` junto com provider/model diferentes e recusado; as regras de delegacao (provedores permitidos, limites, aprovacao de contexto) valem igual. So nome, provedor, modelo e esforco chegam aos agentes.
- Correcao do mesmo filho: `continuationOf` retoma a sessao anterior so se provedor, modelo, esforco, modo, escopo, conta e area forem identicos; senao a chamada e recusada com o motivo e uma sessao nova exige novo pacote aprovado.
- Filhos recebem `read_task_context`, `record_task_memory`, `find_in_workspace`, `read_file_range`, `test_evidence` e `read_task_skill` (nunca `delegate_to_agent`); o pai recebe delegar + as duas de contexto + `read_task_skill`. So o anunciado ao papel e chamavel.
- **Skills sob demanda**: `read_task_skill` carrega as skills ja empacotadas em `resources/skills/` (`task-delegation` so para o pai, `task-memory` para pai e filho) apenas quando o agente pede; o resumo permanente traz so um ponteiro. O nome vem de um enum fixo (nunca um caminho), a resposta traz a versao (hash) e, na mesma sessao, uma releitura so devolve a versao a menos que `reload=true` (use apos compactacao). `dashboard-token-efficiency` e um guia manual e nao e carregado por aqui. Sem MCP compativel (ex.: Gemini) so vale o resumo minimo. O app procura os arquivos em `<pasta do app>/resources/skills` e em `<recursos do pacote>/skills`; se faltarem, a ferramenta falha com mensagem clara e nenhuma instrucao e inventada.
- **Edicao delegada nao suspende o pai**: nenhum mecanismo verificavel faz isso (o pai pode chamar outras ferramentas em paralelo). O app so impede outras execucoes na pasta. Em Configuracoes > Delegacao a opcao `requireParentSuspension` recusa delegacoes de edicao enquanto essa garantia nao existir.

## Permissoes dos agentes ("Sempre permitir")

No modo headless as CLIs nao conseguem perguntar nada: o que exigiria permissao era simplesmente negado (o Claude so listava as "acoes negadas"). Agora cada CLI responde de acordo com o que ela permite:

- **Claude**: pop-up. O dashboard passa `--permission-prompt-tool` apontando para a ferramenta MCP local `permission_prompt`; cada acao que exigiria permissao chega ao dashboard, que decide por **regra** ou pergunta a voce (permitir uma vez, sempre permitir ou negar). Sem resposta em 5 min (configuravel) a acao e negada; se o agente pai for cancelado, a conexao cair ou o app reiniciar, o pedido pendente expira.
- **Codex**: nao ha pop-up no `codex exec`; "sempre permitir" vira **politica de sandbox**: rede dentro da sandbox `workspace-write` (`network_access`) ou, com ciencia explicita do risco, `danger-full-access`. Delegacoes somente leitura continuam `read-only`, sempre.
- **OpenCode**: tambem sem pop-up no `opencode run`; "sempre permitir" vira `--auto` (aprova tudo que nao esteja explicitamente negado) e as regras de comando viram permissoes `bash` na configuracao inline (negar vence).
- **Regras** (tabela `permission_rules`): por agente, por comando exato ou prefixo (`npm run *`), opcionalmente por projeto; ficam em Configuracoes > Permissoes. Pedidos e decisoes ficam registrados (`permission_requests`, os ultimos 2.000).
- **Protecao**: um curinga so vale para comandos *simples*; encadeamento, pipe, redirecionamento, substituicao (`$( )`, crases), `%VAR%` e quebras de linha voltam a perguntar (`npm run *` nunca libera `npm run x && rm -rf /`). Regra ampla (`*`, `git *`, `powershell *`, `node *`...) exige ciencia explicita do risco; curinga sobre comando destrutivo (`rm *`, `git reset --hard *`, `sudo *`...) e sempre recusado; comando destrutivo so passa por regra **exata** e reconhecida. O padrao escolhido no pop-up precisa cobrir o pedido real. Negar vence permitir.
- `PermissionPrompt.tsx` está montado em `App.tsx`; `PermissionRules.tsx` fica em Configurações > Permissões. IPC: `listPermissionRequests`, `resolvePermissionRequest`, `listPermissionRules`, `addPermissionRule`, `removePermissionRule`, `assessPermissionRule`, `getPermissionSettings`, `setPermissionSettings`; eventos `permissionRequest`/`permissionResolved` no canal do chat.
- **Limites**: o fluxo do Claude foi testado com CLI falsa e testes unitarios; `--permission-prompt-tool` **nao** foi exercitado com o Claude real (exigiria uma execucao paga). Nao existe aprovacao por comando no Codex/OpenCode neste modo (exigiria o App Server do Codex e o servidor do OpenCode, nao adotados). O bloqueio de comandos por outras camadas (regras da propria sessao de desenvolvimento, politicas do sistema) nao e contornado por estas regras.

## Memoria por tarefa e consentimento de contexto

Cinco coisas separadas: **historico** (auditoria, nao vai ao prompt sozinho), **memoria** (itens curtos `objective/constraint/decision/todo/finding/validation/checkpoint` com origem, escopo, evidencia por hash e validade), **pacote** (snapshot imutavel de itens para um destinatario), **sessao nativa** (contexto que a CLI ja recebeu) e **artefato** (resultado completo, recuperavel por referencia). Tudo fica no SQLite do app (fora das pastas que os agentes leem) e nunca cruza tarefas, nem quando compartilham a mesma pasta.

- **Consentimento**: contexto que ja existe (memoria, historico, `context` textual) so segue a outro destinatario, sessao, perfil ou provedor depois que voce aprova o pacote exato: a aprovacao vale para aquele conteudo (hash), emissor, provedor/perfil/modelo/esforco, area e escopo. Editar o pacote, trocar de modelo/perfil/area ou substituir a sessao exige novo pedido; um segundo clique e inofensivo; recusar envia so a ordem direta (sem resumo, titulo ou versao comprimida do que foi recusado) e a delegacao continua. A ordem direta do pai (`objective`) nao precisa de aprovacao. O resultado novo do filho volta ao pai automaticamente. A espera pela sua decisao nao conta no timeout do filho; se o pai cancelar, o transporte MCP expirar ou o app reiniciar, o pedido pendente e invalidado (aprovar depois nao inicia nada).
- **Uma regra so para entrega e consulta**: cada execucao recebe do backend uma **identidade efetiva** (tarefa + destinatario completo + sessao nativa, vinculada quando o executor a informa; nunca escolhida pelo agente). Indice, item, trecho, artefato e delegacao passam pela mesma verificacao da entrega (estado aprovado, hash recomputado, destinatario e sessao). Uma sessao nova ou substituta, mesmo na mesma conversa, nao herda memoria, pacotes nem artefatos da anterior sem novo pedido; a continuacao da mesma sessao continua funcionando. Dados anteriores a esta regra ficam sem identidade e exigem nova aprovacao (nada e apagado; o painel do usuario continua vendo tudo).
- **Mensagem retida** (troca de provedor, sessao nova, worktree): o envio fica em `pending_sends` com o texto e o destino escolhidos; a tarefa fica reservada contra envio duplicado; aprovar (ID do envio + hash exibido) executa **no destino original**, mesmo que a selecao da tela tenha mudado. Consentimento (`approved`) e entrega (enviado com confirmacao pendente, entregue, falhou) sao estados separados na tela e no IPC (`delivery`). O prazo so expira o pedido: nunca inicia a execucao.
- **Selecao do contexto (sem IA)**: o candidato reune, por regra e ordem fixas, objetivos e restricoes, decisoes, pendencias abertas e as evidencias de teste mais recentes ainda validas das conversas da tarefa (nunca a memoria privada de filhos), rotula item sem evidencia como "validade desconhecida" e o historico bruto so completa o espaco que sobrar. Itens ja confirmados para o mesmo destinatario e sessao (identidade + revisao + conteudo) nao se repetem. O que **nao coube** (limite de itens ou caracteres, item grande demais, desatualizado) aparece no pedido, com aviso destacado se for um objetivo ou restricao; nao entra no hash e nunca e enviado.
- **Revogar** impede envios futuros; o que o provedor ja recebeu nao pode ser apagado (para continuar sem isso, use uma sessao nova).
- **Entregas** ficam registradas por pacote e sessao: itens ja confirmados nao sao reenviados, so revisoes novas aprovadas; envio interrompido fica "incerto" e nunca e tratado como confirmado.
- **Limites** (Configuracoes; valores iniciais, nao promessas): pacote 6.000 caracteres / 8 itens / 2.000 por item; conclusao 3.000; consulta 6.000 e 10 resultados por pagina; espera pela aprovacao 10 min; resumo de regras do runtime ~500 tokens estimados. Excedeu: o pedido e recusado explicando como escolher itens, dividir ou ampliar; nada e cortado em silencio.
- **Sem LLM extra**: memoria e registrada pelo usuario/agente (`record_task_memory`) e por fatos deterministicos (resultado de delegacao, checkpoint reunido por regra em conclusao de unidade de trabalho). Busca por tipo, caminho e texto normalizado no SQLite; sem embeddings.
- **Evidencia**: itens com arquivos de apoio guardam o hash do conteudo; arquivo alterado marca o item DESATUALIZADO; sem evidencia declarada a validade e "desconhecida". Testes registrados por `test_evidence` ficam marcados como **relato do agente** (`agent_reported`): o dashboard so recebeu o texto e nao observou a execucao, e o endpoint chamado pelo agente nao consegue se declarar `executor_observed`. A consulta compara o comando **exato** (caixa, acentos e espacos dos argumentos contam) e o diretorio real, reenumera as raizes de dependencia declaradas (arquivo novo, removido ou renomeado invalida) e inclui configuracoes e lockfiles da raiz. Mesmo com tudo igual, o relato so informa "as dependencias seguem iguais": nao autoriza pular o teste. `reusable: true` exige execucao observada pelo dashboard, com sucesso, dependencias completas, ambiente comparavel e sem rede; **nao existe hoje captura confiavel ligada a esta ferramenta**, entao nenhuma consulta do agente devolve `reusable: true`. Falha fica preservada para diagnostico e nunca dispensa nova execucao. `read_file_range` devolve um `readToken` (recibo em memoria por sessao, vinculado ao caminho real, hash completo e intervalo exato) e so suprime a repeticao **exata** e inalterada; `ifHash` isolado nao esconde mais nada.
- **Limite honesto**: `objective` e texto livre e pode carregar contexto copiado; o app rejeita referencias estruturadas nao autorizadas mas nao classifica semanticamente o texto. As memorias/imports nativos de cada CLI (auto-memory do Claude, GEMINI.md etc.) nao foram investigados nem controlados por este app.
- **Contabilidade** (tabela `usage_records`): uma linha por execucao/delegacao com entrada, saida, cache lido/gravado e raciocinio como cada provedor informa (campo ausente = NULL, nunca 0), tamanho do prompt montado, contexto anexado, retorno, ferramentas executadas (`tool_calls`: **nao** sao chamadas ao modelo, que nenhuma CLI informa de forma comparavel), retries e duracao. Cada total agregado carrega a soma conhecida e a **cobertura** (`complete`, `partial` ou `unavailable`, com registros conhecidos/esperados): a interface mostra "total conhecido (parcial)" quando faltar qualquer componente e "—" sem dado, nunca zero; cache ou raciocinio sem rotulo do provedor tornam o total ambiguo (parcial). Comparar estrategias so conclui com cobertura completa e a mesma condicao de cache. O painel identifica pai, filhos e retrabalho (continuacoes, delegacoes que falharam, tentativas). Acumulado do thread (Codex) vira delta so com base comparavel; reinicio/compactacao nao gera delta negativo. Cache e raciocinio so somam quando o provedor os rotula como separados. Pai e filhos somam sem dupla contagem. Nao e o prompt oculto da CLI nem cota de assinatura, e nenhuma economia percentual e afirmada: `src/main/fixtures/reference.json` traz so o tamanho de payload de cenarios simulados.

## Banco de dados e migracao

O SQLite fica em `dashboard.db` na pasta de dados do app: `%APPDATA%\gaming-planning-dashboard` no Windows, `~/Library/Application Support/gaming-planning-dashboard` no macOS e `~/.config/gaming-planning-dashboard` no Linux (`$XDG_CONFIG_HOME` se definido). O nome vem do `name` do package.json, igual em `npm run dev` e no app instalado (o `productName` "Orbita" so nomeia o executavel/instalador). A mesma pasta guarda backups automaticos, snapshots (`production`), anexos e `diagnostics.log`. O banco usa migracoes versionadas (`PRAGMA user_version`), cada uma em transacao. Antes de migrar um banco existente o app grava uma copia consistente `dashboard.db.v<versao>.<data>.bak`; um banco de versao mais nova que o app e recusado sem alteracao. As versoes 6 e 7 acrescentam uso, memoria, pacotes, entregas e artefatos sem tocar no historico; a 9 a identidade efetiva de execucao (dados legados ficam sem identidade, nada e apagado), a 10 renomeia o contador `calls` para `tool_calls`, a 11 as mensagens retidas e a 12 o que nao coube num pacote. A 13 preserva falas separadas, a 14 aprovação parcial de contexto, a 15 etapas de trabalho e a 16 execuções de comandos locais. As versões 17–19 acrescentam catálogo/versões de assets, playtests e snapshots de builds; dados anteriores são preservados. A to-do e as configurações de comandos usam settings; migrações antigas permanecem intactas. A versao 3 converteu pins em tarefas (estado, branch e worktree preservados) e cada chat geral antigo em uma tarefa "Chat legado" propria, sem misturar contextos. Para ensaiar sobre uma copia (imprime so contagens): `npm run migration:check -- "%APPDATA%\gaming-planning-dashboard\dashboard.db"` (macOS: `npm run migration:check -- "$HOME/Library/Application Support/gaming-planning-dashboard/dashboard.db"`; Linux: `"$HOME/.config/gaming-planning-dashboard/dashboard.db"`). Se o banco nao abrir, o app mostra o motivo numa caixa de dialogo e registra em `diagnostics.log`.

## Testes

```bash
npm run typecheck
npm test                 # testes com processos/CLIs simulados: nenhuma chamada paga
npm run build && npm run e2e   # abre o Electron real com CLIs falsas e um banco legado sintetico (pasta de dados temporaria)
npm run build && npm run dev:sandbox   # segunda instancia isolada (pasta de dados temporaria, porta de debug propria) para testar correcoes sem fechar o app em uso
```

O e2e e a sandbox abrem o renderer **compilado** (`out/`), nunca um servidor de desenvolvimento herdado do ambiente (`ELECTRON_RENDERER_URL` e removida), e so encerram o processo que criaram.

Opcionalmente, no PowerShell, defina `$env:GPD_GODOT_EXE = 'C:\Tools\Godot\godot_console.exe'` antes de `npm run e2e`. O harness importa, verifica scripts, executa três frames, exporta e inicia o executável de um jogo temporário com essa engine; requer Godot 4 e templates Windows instalados. Sem a variável, as verificações nativas de Godot são puladas e o fluxo MCP continua simulado. Nenhum projeto real é usado.

O E2E tambem grava capturas de tela (1400x900, 1024x768, 768x1024) em `%TEMP%\gpd-e2e-shots`. Nada disso usa suas contas, seus dados ou creditos. Testes contra as CLIs reais (login completo, mensagens, Opus -> Luna) sao manuais e pagos: ver "Limites conhecidos".

## Limites conhecidos

- Nao validado com chamadas reais (exigem uso pago/autorizacao): envio e retomada de mensagens em cada provedor, os campos de uso dos eventos do Claude/OpenCode, o formato do arquivo de sessao do Codex usado para o contexto, o fluxo real de delegacao Opus -> Luna e o login OAuth completo da segunda conta Claude.
- **Gemini**: nesta maquina o Gemini CLI 0.60.0 falha na autenticacao com `IneligibleTierError` (login pessoal recusado pelo Google); o app mostra o diagnostico, mas nao altera `~/.gemini/settings.json`.
- Codex: os chats usam `codex exec --json` (validado); contexto ocupado vem do arquivo de sessao (formato nao documentado) e o uso acumulado do `exec`. Migrar a execucao para o App Server daria contexto ao vivo.
- Delegacao de edicao: o app impede outras execucoes na mesma pasta, mas nao consegue impedir tecnicamente que o proprio agente pai edite em paralelo enquanto espera (a chamada e sincrona).
- Nenhum evento de compactacao foi observado; as medidas vem da ultima chamada de cada execucao. Semantica conferida com dados reais (so numeros, gratuito) apenas no arquivo de sessao do Codex 0.147.0 (`cached_input_tokens` dentro de `input_tokens`, `reasoning_output_tokens` dentro de `output_tokens`, total = entrada + saida, `total_token_usage` cumulativo); o formato do `turn.completed` e os campos de uso de Claude, OpenCode e Gemini (incluindo `cached`) seguem nao validados.
- Nao validado com CLIs reais: as ferramentas MCP de contexto para filhos (em especial Claude com `--tools Read,Grep,Glob` mais MCP) e o carregamento de `read_task_skill` pelas CLIs reais (testado so com clientes MCP simulados).
- **Economia deste ciclo não foi medida com provedores reais.** `read_file_range` aplica queryChars ao conteúdo, com corte explícito e continuação por linhas; cabeçalho é adicional e corte não emite recibo de leitura completa. A integração Godot acrescenta somente consultas específicas sob demanda, paginadas e com detalhes recuperáveis. Os testes e `src/main/fixtures/reference.json` medem caracteres de payload simulado, não tokens do provedor, quota ou qualidade. Não houve mudança adicional de roteamento, cache, memória ou contabilidade. Scripts/bench são experimentos separados; medir ganho real exige benchmark autorizado com o mesmo modelo, esforço, tarefa e condição de cache.
- A interface de aprovacao (cartao de decisao acima do compositor), o painel de memoria/uso/contexto e as mensagens nao enviadas existem na tela, e os limites de contexto ficam em Configuracoes.
- Leitor de tela nao foi testado; contraste e foco foram verificados por calculo/inspecao.
- Sistemas: Windows, macOS e Linux (terminal: `cmd.exe` no Windows, Terminal.app no macOS, x-terminal-emulator/gnome-terminal/konsole/xterm no Linux; cancelamento: `taskkill` no Windows, SIGKILL no grupo de processos nos demais). O CI roda typecheck, testes unitarios e o e2e (`npm run e2e`, Electron real com CLIs falsas e PATH isolado; no Linux sob `xvfb-run`) nos tres; `dev:sandbox` tambem roda nos tres.

## Organização do código

index.ts compõe Electron, valida IPC e liga os serviços. chatService.ts mantém envio/consentimento/execução; jarvisService.ts mantém o assistente da home; linkedinService.ts isola cofre/OAuth/publicação. planning.ts persiste a to-do; workflows.ts controla sequência e revisão; commands.ts executa processos locais; godot.ts lê projetos e prepara argumentos, godotFlow.ts valida receitas/exportações e godotTools.ts atende consultas MCP por organizador. production.ts guarda e revisa assets/builds; playtests.ts registra testes humanos e vínculos a problemas; backups.ts copia/restaura dados e backupGate.ts coordena a pausa do IPC; worktrees.ts integra/remove checkouts com revisão humana e worktreeTasks.ts atualiza seus vínculos e sessões. Estes módulos não importam Electron e usam SQLite e helpers existentes, sem novas dependências.

Os comandos de cada agente ficam em src/main/adapters.ts.
